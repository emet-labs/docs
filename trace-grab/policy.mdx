title: "Policy configuration"
description: "Reference for tracegrab.yaml: dispositions, path syntax, rule resolution, and time handling."
---

The file `tracegrab.yaml` changes the default disposition for single fields. The default disposition tokenizes strings and passes everything else. You do not need this file. With no file, trace-grab uses the safe default.

```yaml
reveal:
  - outputs.status
  - inputs.currency
drop:
  - inputs.patient_id     # remove entirely, even the linkage is sensitive
time: shift               # keep all intervals, destroy absolute timestamps
```

## Keys

The valid top-level keys are `version`, `reveal`, `tokenize`, `drop`, and `time`. Any other top-level key is an error. The CLI exits with a non-zero code and writes no corpus.

## Dispositions

| Disposition | Meaning |
| --- | --- |
| `reveal` | Passes the value unchanged. No tokenization. |
| `tokenize` | Replaces the value with a `TOK_` token. Write it in the configuration only to narrow a `reveal` rule that is too broad. |
| `drop` | Removes the field, including its linkage. |
| `default` | No rule matched. The built-in disposition applies. Pass-verbatim fields pass. String leaves become tokens. Numbers, booleans, and null pass. |

## Path syntax

Policy entries use the same dotted paths that `report.md` prints.

- `.` separates object segments. Example: `inputs.user.email`.
- `*` matches exactly one segment. The path `inputs.*.email` matches `inputs.user.email`. It does not match `inputs.user.profile.email`.
- `**` matches zero or more segments. The path `inputs.**` matches `inputs` and all of its descendants.
- A literal `[*]` suffix on the parent segment matches array elements. Example: `inputs.items[*].sku`.

There is no escape syntax. You cannot target a source key that contains `.` or a wildcard token without ambiguity. Copy the exact path from the generated report.

## How trace-grab resolves rules

For a concrete path, trace-grab does these steps:

1. It collects every rule in `reveal`, `tokenize`, and `drop` whose pattern matches the path.
2. If no rule matches, it applies `default`.
3. Otherwise, it finds the most specific matching rule. It compares the number of literal segments first. It then compares the total number of segments. A rule with fewer wildcards wins.
4. If one rule is the most specific, its disposition wins.
5. If more than one rule has the same specificity, the most restrictive disposition wins. The order is `drop`, then `tokenize`, then `reveal`.

When two rules have the same specificity, the rule that removes more information wins. A security configuration must fail closed.

### Example: narrow a reveal that is too broad

```yaml
reveal:
  - inputs.**
tokenize:
  - inputs.auth.secret
```

Both rules match `inputs.auth.secret`. The exact `tokenize` path is more specific than `inputs.**`. The secret becomes a token. The other input strings stay revealed.

## Required fields

You cannot remove these top-level record fields: `id`, `trace_id`, `parent_id`, `name`, `kind`, `start`, `end`, `status`, `error.kind`, `error.message`, and `source.vendor`.

You also cannot remove these structurally required fields: `labels[*].key`, `labels[*].value`, `links[*].trace_id`, and `links[*].span_id`.

For these fields, `drop` falls back to the next most restrictive option:

- String fields (`id`, `name`, `error.message`, and others): `drop` becomes `tokenize`.
- Non-string fields (for example a numeric `labels[*].value`): `drop` becomes `default`, and the value passes.
- `status`: always passes. It is an enum and not free text.

A `drop` on a key inside a bag removes that key from the output object. Examples are `inputs.user.email` and `unmapped.note`. The fallback applies only to the required fields above.

## Rules that match no path

A rule that matches no path in the corpus appears in the `warnings` array of `manifest.json`. It also appears in `report.md`. This is a common redaction failure. A rule uses a field name that the author remembered wrongly, and it silently matches nothing.

Treat each unmatched-rule warning as a configuration error. Investigate it.

## Time handling

```yaml
time: shift
```

The value `shift` applies one constant offset to every `start` and `end` value in the corpus. trace-grab derives the offset from your salt. The offset is the same across batches. Ordering and all intervals stay. Absolute position does not stay.

The default value is `time: absolute`. It leaves timestamps unchanged.
