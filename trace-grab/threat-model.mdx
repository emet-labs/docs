---
title: "Threat model"
description: "What trace-grab protects against, and what it does not protect against."
---

`trace-grab` reduces the amount of readable trace content in a corpus before the corpus leaves your environment. It does not make a trace corpus harmless, anonymous, or safe for unrestricted distribution.

## Scope and trust boundary

You control these items:

- the source export
- the machine that runs the CLI
- `tracegrab.yaml`
- the salt
- the keymap
- the output directory
- the decision to transfer the bundle

`trace-grab` sends nothing to Emet. You do any transfer yourself, as a separate action.

`trace-grab` reads file sources locally. The opt-in LangSmith API source contacts only the configured LangSmith base URL. It fetches records from that URL. It does not upload a corpus. `trace-grab` has no Emet upload endpoint, telemetry, analytics, or error-reporting service.

This model assumes that the machine and the operator are trustworthy while the tool runs. The source data and the policy can contain mistakes. The model does not assume that they are actively malicious.

## What the tool protects against

With no policy, trace-grab replaces string values with stable `TOK_…` pseudonyms before it writes the bundle. This applies to string values outside the documented pass-verbatim fields. A string is readable in the bundle only in two cases. It belongs to one of those fields, or a `reveal` rule matches it.

A `drop` removes an optional field, including its linkage. Required fields cannot be removed. They fail closed, as [Policy configuration](/trace-grab/policy) describes.

The generated `report.md` lists the observed paths and the plaintext dispositions. You can inspect the result before you transfer it.

These controls reduce accidental disclosure of string content that you did not choose to reveal. They do not inspect whether a value looks sensitive. They do not classify personal data. They do not prove that a configured policy is appropriate.

## Information that remains visible

The bundle keeps the structure that analysis needs.

- **Tool, span, and run names pass unchanged.** A name such as `notify_bankruptcy_counsel` can disclose sensitive business or personal context alone. Span kind, status, `error.kind`, and source vendor also pass.
- **Object keys and native label keys pass unchanged.** Names of input, output, attribute, and unmapped fields show the schema of the application. Label keys show its annotation vocabulary. This is true even when trace-grab tokenizes or drops the associated values.
- **Linkage survives tokenization.** Equal source strings get equal tokens. These stay visible: trace topology, parent and child relationships, links, ordering, and the frequency of repeated values. This is the analytical purpose of tokenization. It is also a class of disclosure. Use `drop` when the relationship must not survive.
- **Numbers and booleans pass by default.** They can carry sensitive meaning, although they are not string content.
- **Timing and volume stay observable.** With the default `time: absolute`, you can see absolute timestamps, intervals, ordering, and record counts. The setting `time: shift` removes absolute position. It keeps intervals and ordering. It does not hide traffic volume.
- **Explicit reveals are plaintext.** A `reveal` rule is an instruction to include the matching values. The tool does not override it.

Stable tokens can also support inference. The basis can be repetition, surrounding structure, timing, volume, or outside knowledge. Tokenization is not encryption of the corpus. It does not claim to prevent such inference.

## Salt and keymap

The salt keeps token assignment stable across batches. The optional file `.trace-grab/keymap.jsonl` maps tokens back to their original values. This lets you interpret findings.

The keymap is a re-identification file. It is stored on your disk with mode `0600`. The CLI never includes it in the bundle. The flag `--no-keymap` prevents its creation.

Anyone who obtains the keymap can recover every value that it records. Protect it separately from the transferred corpus. The tool does not manage backups, access control beyond the local file mode, retention, or deletion of your local files.

## Pseudonymization is not anonymization

You can describe the output as sanitized, de-identified, or pseudonymized. None of these words means that `trace-grab` produces anonymous information. Stable pseudonyms can remain personal data. This is the case when a person can be identified with the separately held keymap, the source data, or other information.

The UK Information Commissioner's Office states that pseudonymized personal data stays within data-protection law for a party that holds the additional identifying information. It describes pseudonymization as a measure that reduces risk and improves security. It does not describe it as a way to stop the law from applying.

`trace-grab` does not make legal determinations. It never claims to produce "fully anonymized" data.

## Threats this tool does not address

`trace-grab` does not defend against these threats:

- a compromised machine, runtime, dependency, shell, filesystem, or user account
- an operator who deliberately reveals or transfers sensitive fields
- a policy that is mistaken, too broad, or malicious
- access to the original export, salt, keymap, API credential, or other local files
- re-identification or inference that uses visible names, keys, topology, linkage, timing, volume, or outside information
- denial-of-service inputs, resource exhaustion, or an unavailable source API
- source telemetry that is false, incomplete, or misleading
- tampering after generation

On the last item: the digest in the manifest detects changes to the corpus when you check it against a trusted manifest. It is not a signature. It does not establish authorship.

The tool also does not upload, approve, retain, or delete a transferred corpus for anyone else. These are operational and governance responsibilities outside this CLI.

## Claims that you can verify

Each claim below is something that you can check yourself. Do not accept it on trust.

| Claim | How to verify |
| --- | --- |
| trace-grab never contacts an Emet endpoint. The source contains none. | `grep -ri emet src/` prints nothing |
| There is no telemetry, analytics, or update check. | `grep -riE "telemetry\|analytics\|update.?check" src/` prints nothing |
| There is no `postinstall` script. | `jq '.scripts.postinstall // "absent"' package.json` prints `"absent"` |
| There is one runtime dependency. | `jq '.dependencies \| length' package.json` prints `1` |
| No network primitive exists outside the single fetcher module. | `bun test test/no-egress.test.ts` |
| No Bun-specific API exists in the shipped `src/`. trace-grab runs under plain Node 20 or later. | `bun test test/no-egress.test.ts` |
| The corpus leaves your machine only when you send it. | trace-grab has no upload command. |

The published package carries SLSA provenance. This is a build attestation that ties the tarball to a commit and a workflow run. It is signed with sigstore. To verify it, check the "Provenance" badge on the [npm package page](https://www.npmjs.com/package/@emetlabs/trace-grab). You can also check the entry in the [sigstore transparency log](https://search.sigstore.dev).

Publishing uses GitHub OIDC trusted publishing. trace-grab does not store or use an npm access token.
