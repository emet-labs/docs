Sentinel checks what your systems did against Specifications that you write and review. It reports a Verdict and the evidence behind the Verdict.

Many AI agents and automated jobs act across several applications. Each application logs only its own part. No single log shows the full sequence. Sentinel joins the parts and checks the sequence.

## Who Sentinel is for

Sentinel is for teams that run AI agents or automation with high impact. Examples are payments, infrastructure changes, tickets, and approvals.

You use Sentinel when you must answer this question: what did the deployment do, and is the evidence strong enough to trust the answer?

## The one rule

Missing evidence is never a pass.

If evidence is absent or incomplete, Sentinel reports `Inconclusive`. It names what is missing. Sentinel reports `Satisfy` only after Evidence Coverage closes.

This rule shapes the whole product. When Sentinel cannot tell, it says so.

## What Sentinel reports

A Verdict has an outcome and an authority.

| Part | Values |
| --- | --- |
| Outcome | `Satisfy`, `Violate`, `Inconclusive` |
| Authority | `Provisional`, `Authoritative` |

Each Verdict links to its Assurance Envelope. The Assurance Envelope lists the sources, gaps, Watermarks, and Filter epochs behind the Verdict. For details, see [How Sentinel works](/sentinel/how-it-works).

## What works today

Read this list before you plan a rollout.

- Sentinel detects. It does not block. Every Specification runs in Shadow.
- You run Sentinel yourself. It ships as a self-hosted server. You build it from the repository.
- The server has no authentication. It binds to loopback by default. Do not expose it on a public network.
- You register sources in a JSON file. No HTTP route registers a source.
- Seven Probe SDKs exist. No SDK is on a public package registry yet. See [Probe SDKs](/sentinel/sdk/index).
- Sentinel has no multi-tenant mode. See [Multi-tenant setup](/sentinel/multi-tenant-setup).
